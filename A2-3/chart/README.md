## 3. 실행

```bash
pip install -r chart/requirements.txt
cp chart/.env.example chart/.env      # GEMINI_API_KEY 를 넣습니다
```

레포 루트에서 실행합니다. `main.py` 는 `chart/main.py` 를 불러주는 런처입니다.

```bash
python main.py import --file source/input/cosmetics_reviews_100.csv   # 수집 → 정제 → DB
python main.py analyze --unanalyzed --limit 25                        # 감정 분석 (C)
python main.py extract                                                # 인사이트 추출 (C)
python main.py dashboard                                              # 차트 7장 + 리포트
```

## 4. 설계 결정과 근거

이 파트에서 실제로 시간을 쓴 곳입니다. 코드보다 **왜 그렇게 했는지**가 남습니다.

### 4.1 감정 분석에 별점을 넘기지 않는다

`analyze` 는 DB에서 13개 키를 읽어오지만 C에게는 **두 개만** 넘깁니다.

```python
payload = [{"id": r["id"], "review_text": r["review_text"]} for r in reviews]
```

`rating` 이 프롬프트에 들어가면 모델이 별점을 그대로 따라갑니다.
그러면 품질 지표인 **별점-감정 일치도가 항상 100%** 가 되고, 순환논리라 아무것도 못 재게 됩니다.
주석이나 합의로 막지 않고 **넘기는 키를 줄여서 구조적으로** 막았습니다.

실제 측정값은 **81.8%** 로 나왔습니다. 100%가 아니라는 것 자체가 지표가 살아 있다는 증거입니다.

### 4.2 집계는 `stats.py` 한 곳에서만

차트가 자기 손으로 세고 리포트가 또 세면, 같은 데이터인데 차트는 89건 리포트는 90건이 되는 일이 반드시 생깁니다.
반올림 방식이나 미분석 포함 여부 같은 사소한 차이로 갈립니다.

그래서 `calculate_stats()` 하나가 6칸을 만들고, 쓰는 쪽은 자기 칸만 봅니다.

```python
{
    "meta":       {...},   # 생성 시각 · 필터
    "summary":    {...},   # ← 리포트(C)
    "chart_data": {...},   # ← 차트(A)
    "quality":    {...},   # ← 리포트(C)
    "top_n":      {...},   # ← 리포트(C) · 개선 우선순위 포함
    "alerts":     [...],   # ← CLI · 리포트. 임계치 판정 결과 (4.10)
}
```

KPI 요약 타일까지 이 규칙을 지킵니다. `chart_data["kpi_summary"]` 는 **새로 세는 값이 하나도 없고**
`summary` · `quality` 에서 옮겨오기만 합니다. 검증기가 이걸 직접 확인합니다.

```python
if kpi["total"] != summary["total"]:
    problems.append("KPI 는 다시 세지 않고 옮겨오기만 해야 합니다.")
```

### 4.3 중복 판정은 DB에서, 정규화된 해시로

B의 cleaner 는 **이번 파일 안의 중복**만 볼 수 있습니다. **이미 DB에 있는 중복**은 DB만 압니다.
그래서 `(product_name, review_text, review_date)` 를 공백 정규화·소문자화한 뒤 SHA-256 을 내고,
`reviews.review_hash` 에 UNIQUE 를 걸어 그 위에서 정책을 갈랐습니다.

```
skip   → INSERT OR IGNORE
upsert → INSERT ... ON CONFLICT(review_hash) DO UPDATE
```

세 컬럼에 그냥 composite UNIQUE 를 걸어도 될 것 같지만 두 가지가 새어 나갑니다.

- **정규화** — `"좋아요"` 와 `"좋아요 "` 가 다른 행이 됩니다. 같은 CSV 를 두 번 넣을 때마다 DB가 불어납니다
- **NULL** — SQLite 의 UNIQUE 는 NULL 을 서로 다른 값으로 봅니다. `add -t "..."` 를 `--product` 없이 두 번 치면 못 막습니다. 해시는 `None` 을 `""` 로 정규화해서 막습니다

### 4.4 실패를 한 칸 안에 가둔다

세 군데에서 같은 원칙을 씁니다.

| 상황 | 처리 |
|---|---|
| 리뷰 한 건 분석 실패 | 그 id 만 `failed_ids`, 나머지는 저장. 종료 코드 2 |
| 차트 한 장 실패 | 로그 남기고 나머지 6장 + 리포트는 그대로 |
| matplotlib 미설치 | `ImportError` 만 따로 잡아 차트를 건너뛰고 통계·리포트는 출력 |

100건 돌리다 50번째에서 API 가 흔들렸다고 앞의 49건을 버리면 안 됩니다.
그림 하나 때문에 통계까지 못 보게 되는 것도 마찬가지고요.

### 4.5 계약 검증을 저장 **앞에** 둔다

`interfaces.py` 가 C의 결과를 받자마자 확인합니다. 어긋나면 **DB에 값이 들어가기 전에** 멈춥니다.

- `results` / `failed_ids` 키 존재
- 각 `id` 가 int 이고 중복이 없는가
- 성공과 실패에 **같은 id** 가 들어 있지 않은가
- `sentiment` 가 세 값 중 하나인가, `confidence` 가 0.0~1.0 인가

사람을 못 믿어서가 아니라, 나중에 코드를 고쳤을 때 **조용히 틀린 값이 쌓이는 걸** 막으려는 장치입니다.

### 4.6 차트 색은 검증기를 돌려서 골랐다

1차본은 긍정 초록 / 중립 회색 / 부정 주황이었는데 떨어졌습니다.

```
[FAIL] CVD separation   #888780 ↔ #1D9E75  ΔE 1.2 (적록색약)
[FAIL] Normal-vision    #888780 ↔ #1D9E75  ΔE 11.9  (기준 15)
```

적록색약에서 회색과 초록이 사실상 같은 색으로 보입니다. 감정 분포 차트에서 중립과 긍정이 구분되지 않으면
그 차트는 아무 정보도 주지 못합니다.

감정은 `부정 ← 중립 → 긍정` 의 **극성(polarity)** 이라 categorical 이 아니라 **diverging** 입니다.
초록↔빨강은 색약에서 무너지는 대표 조합이라 파랑↔빨강으로 바꿨습니다.

```
[PASS] CVD separation   최악 인접쌍 ΔE 8.7 (deutan) · 12.7 (tritan)
[PASS] Normal-vision    최악 인접쌍 ΔE 16.2
[PASS] Contrast         3색 모두 배경 대비 3:1 이상
```

색만으로 의미가 전달되지 않도록 **모든 막대에 수치를 직접 표기**하고 범례를 항상 넣었습니다.
색 + 위치 + 숫자, 3중 인코딩입니다.

별점 분포 차트만 감정 3색을 안 씁니다. 4점 막대를 긍정색으로 칠하면 **'4점 = 긍정' 이라는 결론을 차트가 미리 내려버립니다.**
그 대응이 실제로 성립하는지 보려고 바로 옆에 '별점별 감정 구성' 을 두는 것이라, 여기서 색으로 답하면 두 차트가 같은 말을 하게 됩니다.

### 4.7 한글 폰트가 없으면 영문으로 떨어진다

폰트를 못 찾은 채로 한글을 그리면 글자가 전부 두부(□□□)로 나옵니다.
깨진 차트가 리포트에 박히는 것보다 영문이 낫습니다.

```python
resolve_font() -> (폰트명, 한글가능여부)   # 못 찾으면 (None, False), 결과는 캐시
```

Windows(맑은 고딕) → macOS(AppleGothic) → Linux(나눔·Noto) 순으로 찾고,
모든 라벨이 `_title(한글, 영문)` 을 거칩니다.
`axes.unicode_minus = False` 도 함께 걸었습니다 — 한글 폰트에는 유니코드 마이너스가 없는 경우가 많아 음수 눈금만 두부로 나옵니다.

### 4.8 B/C 폴더에 파일을 한 줄도 추가하지 않는다

`prompt/` 와 `source/src/` 에는 `__init__.py` 가 없어서 평범한 import 가 안 됩니다.
`__init__.py` 를 하나만 넣어도 그 폴더는 더 이상 그 사람만의 것이 아니게 되고 머지 충돌이 시작됩니다.

그래서 패키지 import 대신 **파일 경로로 직접 모듈을 읽는 로더**를 A쪽에 뒀습니다.

```python
spec = importlib.util.spec_from_file_location("c_analyzer", PROMPT_DIR / "analyzer.py")
```

이렇게 하면 B/C 폴더에 아무것도 안 생기고, `sys.path` 도 오염되지 않아 이름 충돌(`cleaner` 가 둘)이 안 납니다.
통합 테스트에 이 경계를 감시하는 항목도 넣었습니다.

### 4.9 대역(mock)은 연결이 끝나는 순간 걷어낸다

개발 초기에는 API 키 없이 배선을 확인하려고 `modules/mock_ai.py` 라는 규칙 기반 대역을 뒀습니다.
C의 Gemini 연결이 끝난 뒤 **파일과 `--mock` 플래그를 모두 제거**했습니다.

대역이 제품 코드 폴더에 남아 있으면 "지금 도는 게 진짜 분석인가 대역인가" 를 실행할 때마다 플래그로 확인해야 하고,
규칙 기반 결과가 DB에 섞여 들어가도 `model` 컬럼을 열어보기 전까지는 아무도 모릅니다.

테스트와 자가 점검이 쓰던 대역은 **각 테스트 파일 안으로** 옮겼습니다.
그 덕에 키 없이도 통합 테스트 58개와 계약 점검 전체가 그대로 돕니다.

### 4.10 숫자를 내놓는 데서 멈추지 않는다 — 임계치와 급증 감지

집계는 "부정 29%" 를 알려줄 뿐 **그게 높은 건지는 말하지 않습니다.**
판단 기준이 없으면 리포트를 읽는 사람마다 다른 결론을 냅니다.
그래서 임계치를 `config.json` 에 두고 `stats` 가 판정해 `alerts` 칸으로 내보냅니다.

| 코드 | 언제 | 기본 임계치 |
|---|---|---|
| `negative_ratio_high` | 전체 부정 비율이 높을 때 | 경고 15% · 심각 30% |
| `negative_spike` | 직전 구간 대비 부정률이 급증 | +10%p |
| `group_negative_high` | 특정 제품·피부타입의 부정률이 높을 때 | 30% |
| `low_agreement` | 별점-감정 일치도가 낮을 때 | 60% |
| `low_confidence` | 평균 확신도가 낮을 때 | 0.65 |
| `unanalyzed_remaining` | 미분석이 남아 있을 때 (안내) | — |

**판정과 동시에 로그에 남깁니다.** 콘솔 출력만 하면 터미널을 닫는 순간 사라져서
"지난주에 무슨 경고가 떴었지" 를 확인할 방법이 없습니다.

```
2026-08-14 08:10:57 WARNING stats [negative_spike] 부정 비율이 직전 월 대비
급증했습니다 (2025-05) — 2025-04 0% → 2025-05 14% (+14%p, 표본 14건)
| 값 0.1429 / 기준 0.1000
```

코드·범위·수치가 한 줄에 있어서 `grep negative_spike chart/logs/app.log` 로
언제부터 떴는지 추적됩니다. 가설과 참고 지표는 DEBUG 로 내려
파일에는 남기고 화면은 덮지 않습니다.

**표본이 작으면 판정하지 않습니다.** 3건 중 2건이 부정이면 67%지만 그건 경고가 아니라
잡음입니다. `min_bucket_size` · `min_group_size` 로 끊습니다.

**임계치 값의 출처를 분명히 해둡니다.** 업계 표준이 아니라 이 데이터셋 기준의 출발점입니다.
99건에서 부정 4%, 일치도 82% 가 나왔으므로 부정률 15% 는 "평소의 세 배",
일치도 60% 는 "분석이 흔들리는 수준" 입니다. 제품군이나 수집 채널이 바뀌면 다시 잡아야 합니다.

#### 급증했을 때 코드가 하는 말 / 하지 않는 말

원인을 단정하지 않습니다. 코드가 아는 것은 "어디에 몰려 있는가" 까지입니다.

```
[! ] 부정 비율이 직전 월 대비 급증했습니다 (2025-05)
     2025-04 0% → 2025-05 14% (+14%p, 표본 14건)
     · 확인 후보: 제품 '수분 장벽 크림' 에 몰려 있습니다
                 — 이 구간 부정의 50% (전체 평균 25%)
     · 확인 후보: 피부타입 '건성' 에 몰려 있습니다
     · 확인 후보: 이 구간의 부정 리뷰 원문을 표본으로 읽어보세요.
     · 다음 지표: 해당 구간의 생산 로트·유통 경로
     · 다음 지표: 직전 리뉴얼·성분 변경 시점
     · 다음 지표: 동일 기간 경쟁사 리뷰 추이
```

`hypotheses` 는 **확인해볼 후보**, `next_metrics` 는 **다음에 볼 지표**입니다.
결론이 아니라 다음 행동을 가리키는 이름을 일부러 골랐습니다.

#### 경고가 떴을 때의 대응 절차

| 단계 | 할 일 |
|---|---|
| 1 | `python main.py stats` 로 어느 경고인지 확인 |
| 2 | `scope` 가 가리키는 범위로 좁혀 재확인 — `dashboard --product "..."` |
| 3 | `list --sentiment negative --sort rating` 으로 **원문을 직접 읽기** (최소 10건) |
| 4 | `확인 후보` 가 맞는지 원문으로 판단. 아니면 기간 공통 요인을 봄 |
| 5 | `다음 지표` 를 사내 데이터(반품률·클레임)에서 확인 |
| 6 | 조치 후 다음 주기에 같은 경고가 사라졌는지 확인 |

**3번을 건너뛰지 않는 것이 핵심입니다.** 경고는 어디를 볼지 알려줄 뿐이고,
무엇이 문제인지는 원문에만 있습니다.

### 4.11 AI 정확도를 사람 라벨로 잰다 — `review` 명령

감정 분석 정확도를 스스로 잴 수단이 없으면 프롬프트를 고쳐도 나아졌는지 알 수 없습니다.
"그럴듯해 보인다" 로는 v1 과 v2 를 고를 수 없습니다.

`stats` 의 **별점-감정 일치도는 이 검수를 대체하지 못합니다.**
별점은 사람 라벨이 아니라 다른 신호입니다. 별점을 후하게 주는 채널이면
일치도가 낮아도 분석은 맞을 수 있습니다. 정확도는 사람이 매긴 라벨과만 비교됩니다.

#### 세 단계

```bash
python main.py review sample --size 30
#   → chart/output/review_<회차>.csv
#   '검수라벨' 열에 긍정 / 중립 / 부정 을 채웁니다

python main.py review load --file "review_20260814_081402_영휘.csv" --reviewer 영휘
python main.py review load --file "review_20260814_081402_세인.csv" --reviewer 세인

python main.py review score
python main.py review score --list          # 회차 목록
python main.py review score --batch <회차>   # 특정 회차만
```

#### 표본을 뽑는 방식

**계통 추출**을 씁니다. 무작위로 뽑으면 돌릴 때마다 표본이 바뀌어
프롬프트 v1 과 v2 를 같은 표본으로 비교할 수 없습니다.
id 순으로 일정 간격을 띄우면 같은 데이터에서 항상 같은 표본이 나옵니다.

**가장 적은 감정은 통째로 넣습니다.** 99건에서 부정이 4건인데 고르게 뽑으면
부정이 한두 건밖에 안 들어가고, 그러면 "부정을 잘 잡는가" 를 아예 잴 수 없습니다.

```
[INFO] 검수 표본 20건 (분석 99건 중) · 'negative' 4건 전량 포함
```

CSV 는 `utf-8-sig` 로 씁니다. 검수는 대개 Excel 로 하는데 utf-8 로 쓰면
한글이 전부 깨집니다.

#### 검수 시점의 AI 라벨을 함께 박아둡니다

`human_labels` 테이블이 `ai_sentiment` · `ai_confidence` · `ai_model` 을
같이 들고 있습니다.

`analyses` 는 `review_id` 가 UNIQUE 라 **재분석하면 덮어써집니다.**
그러면 나중에 프롬프트를 바꿔 다시 돌렸을 때 "그때 무엇과 비교했는지" 가 사라집니다.
스냅샷을 남겨야 v1 과 v2 의 일치율을 나란히 놓고 볼 수 있습니다.

`(review_id, batch, reviewer)` 가 UNIQUE 라 같은 회차에서 같은 사람이 다시 매기면
덮어씁니다. 검수 파일을 고쳐 다시 넣는 일이 흔한데, 그때마다 행이 늘면
일치율이 조용히 왜곡됩니다.

#### 나오는 지표

```
=== AI 검수 결과 ===
검수 회차: 20260814_081402
검수자   : 세인, 영휘
대상     : 15건 (라벨 40개)

AI-사람 일치율   : 86.7%  (기준 80%) [OK]
검수자 간 일치율 : 75.0%  (20건 · 기준 85%) [미달]
  → AI 보다 라벨 기준이 먼저입니다. 사람끼리 갈리는데 AI 만 고쳐봐야 소용없습니다.

[혼동 방향] AI 판정 → 사람 판정
- 중립 → 부정 : 2건

[확신도 구간별 일치율]
- 0.90~1.00 : 100.0% (10/10)
- 0.80~0.89 :  60.0% (3/5)
  확신도가 높은데 일치율이 낮으면 프롬프트가 잘못된 확신을 주고 있는 것입니다.

[모델·프롬프트 버전별] ← A/B 비교
- gemini-3.6-flash@v2 : 87.0% (20/23)
- gemini-3.6-flash@v1 : 78.0% (18/23)

```

| 지표 | 기준 | 미달이면 |
|---|---|---|
| AI-사람 일치율 | **0.80** | 프롬프트를 손봅니다. 혼동 방향을 먼저 보세요 |
| 검수자 간 일치율 | **0.85** | **AI 가 아니라 라벨 기준부터** 다시 잡습니다 |
| 혼동 방향 | — | `중립↔부정` 이 대부분이면 "완곡한 불만" 을 프롬프트에 명시 |
| 확신도 구간별 | — | 높은 구간에서 낮으면 잘못된 확신을 주는 것 |

**두 사람이 갈리면 임의로 한쪽을 고르지 않습니다.** `disputed` 로 따로 세고
일치율 계산에서 뺍니다. 한쪽을 고르면 "AI 가 틀린 건지 기준이 모호한 건지" 를
가릴 수 없게 됩니다.

일치율이 기준 미달이면 **종료 코드 2** 를 돌려줍니다. CI 에서 걸 수 있습니다.

`analyses.model` 에 버전을 함께 적어(`gemini-3.6-flash@v2`) 같은 표본을 재분석하면,

지켜야 할 것 두 가지입니다.

- **표본을 바꾸지 않습니다.** 바뀌면 프롬프트 때문인지 데이터 때문인지 못 가립니다.
  계통 추출이라 같은 데이터면 같은 표본이 나옵니다
- **한 번에 한 가지만 바꿉니다.** 두 곳을 고치고 좋아지면 어느 쪽 덕인지 모릅니다

되돌릴 때는 `analyze --all --force` 로 전량 재분석합니다.
`analyses.review_id` 가 UNIQUE 라 덮어써지고 행이 늘지 않습니다.
검수 라벨은 `human_labels` 에 그대로 남아 있어서 다시 매길 필요가 없습니다.

#### A가 하지 않는 것

프롬프트를 고치는 것은 C 영역입니다. A는 **고칠 근거가 되는 숫자**를
내놓는 데까지 합니다. 어떤 문장을 넣을지는 이 숫자를 보고 민규님이 정합니다.

### 4.12 파일 형식은 A가 책임진다

`import` 는 CSV 와 Excel(`.xlsx` · `.xlsm` · `.xltx`)을 받습니다.
Excel 이면 A가 첫 시트를 임시 CSV 로 눕혀 B의 `import_reviews()` 에 넘깁니다.

```
in.xlsx ──[A: bridge.xlsx_to_csv]──▶ 임시 CSV ──[B: import_reviews]──▶ raw JSONL
```

**B의 파일은 한 줄도 바뀌지 않습니다.** 정제 규칙도 한 곳에 그대로 남습니다.
"어떤 파일 형식을 받는가" 는 CLI 의 입출력 범위 문제라 A가 지는 게 맞다고 봤습니다.
나중에 세인님이 xlsx 를 직접 읽게 되면 `xlsx_to_csv()` 만 지우면 됩니다.

첫 시트만 읽습니다. 시트가 여러 장일 때 어느 것이 리뷰인지는 A가 알 수 없어서,
지금은 첫 시트로 못 박고 로그에 시트 이름을 남깁니다.
헤더만 있고 데이터가 없으면 **조용히 0건으로 넘기지 않고 예외를 던집니다.**
"import 성공, 저장 0건" 만큼 헷갈리는 결과가 없습니다.

### `stats.py` — 집계 · 판정 (1,036줄)

`calculate_stats(filters)` 하나가 6칸을 만듭니다. 눈여겨볼 두 가지:

**분모가 다릅니다.** `analysis_rate` 는 전체 기준, `sentiment_ratios` 는 분석된 것 기준입니다. 섞으면 숫자가 안 맞습니다.

**추이의 집계 단위를 자동으로 바꿉니다.**

```
14일 이하  → 일별
120일 이하 → 주별 (그 주 월요일 날짜로 표기)
그 이상    → 월별
```

하루 1건씩 들어오는 데이터를 일별로 그리면 누적 차트가 바코드처럼 보여서 아무 정보도 주지 못합니다.

**칸이 6개입니다.** `meta` · `summary` · `chart_data` · `quality` · `top_n` · `alerts`.
`alerts` 는 4.10 절에서 설명한 임계치 판정 결과입니다.

**`top_n["keyword_impact"]` — 개선 우선순위**

C가 뽑은 부정 키워드를 A가 본문으로 되짚어 계량합니다.
C의 `extract` 는 앞의 60건만 프롬프트에 넣으므로 빈도를 알 수 없고,
별점·감정은 DB에만 있습니다. 그래서 세는 일은 A가 맡습니다.

```
1. 유분 증가 (우선순위 0.55) — 8건, 부정 25%, 평균 별점 2.75 (-0.90)
2. 느린 흡수 (우선순위 0.32) — 6건, 부정  0%, 평균 별점 3.17 (-0.48)
3. 무거운 사용감 (우선순위 0.21) — 4건, 부정 0%, 평균 별점 3.50 (-0.15)
4. 트러블 발생 — 본문에서 찾지 못했습니다 (모델이 개념으로 요약한 표현)
```

점수 = 빈도 0.4 + 부정률 0.4 + 별점 하락 0.2. 하나만 보면 어긋나기 때문입니다.
'향' 은 자주 나오지만 긍정도 많고, '고장' 은 드물지만 나오면 1점입니다.
빈도만 보면 앞을, 심각도만 보면 뒤를 고르게 되어 둘 다 틀립니다.

본문 매칭이 까다로웠습니다. C가 주는 키워드는 `무거운 사용감` 처럼 **모델이 요약한
개념**이라 본문에 그대로 없습니다. 실제로 문자열을 그대로 찾으니 다섯 개 중 다섯 개가
0건이었습니다. 그래서 어절을 앞 2글자 어간으로 자릅니다 —
한국어는 `무거운 / 무겁게 / 무거워` 가 앞 두 글자를 공유합니다.

대신 `사용` · `제품` · `피부` 같은 흔한 어절은 뺍니다. 안 빼면
`무거운 사용감` 이 `사용` 때문에 99건 중 72건에 걸려 아무 의미 없는 1순위가 됩니다.

**매칭이 0건이어도 버리지 않고 `matched: false` 로 남깁니다.**
모델이 본문에 없는 말로 요약했다는 뜻이라, 그것 자체가 요약 품질을 의심할 근거입니다.
조용히 지우면 그 신호가 사라집니다.

점수는 **이 데이터 안에서의 상대 순위**입니다. 빈도를 최댓값으로 정규화하므로
리뷰가 바뀌면 같은 키워드도 다른 점수를 받습니다. 제품 간·기간 간 비교에 쓰면 안 됩니다.

### `visualizer.py` — 대시보드 차트 7종 (846줄)

| 파일 | 형태 | 답하는 질문 |
|---|---|---|
| `kpi_summary.png` | 숫자 타일 6칸 | 그래서 몇 건이고 얼마나 부정적인가 |

**입력은 `stats["chart_data"]` 뿐입니다.** 이 파일에서 숫자를 세지 않습니다.

이름 하나가 네 군데를 묶습니다.

```
stats.chart_data 의 키  ==  CHART_ORDER  ==  DRAWERS 키  ==  출력 파일명
```

하나만 오타가 나도 에러가 아니라 **차트가 조용히 한 장 사라집니다.** 그래서 테스트에 `set(chart_data) == set(CHART_ORDER)` 를 박아뒀습니다.

설계 선택 두 가지:

- **추이에 이중 축(dual-axis)을 안 씁니다.** '건수'와 '비율'은 단위가 다른데 y축 두 개를 세우면 두 계열의 교차점이 눈금 맞추기에 따라 마음대로 움직입니다. 아무 의미 없는 교차가 인과처럼 읽혀서, 위아래 패널로 나누고 x축만 공유합니다
- **그룹별 차트는 건수가 아니라 비율로 그립니다.** 5점 33건 / 1점 8건인데 건수로 그리면 막대 길이가 '리뷰가 몇 개인지'만 말합니다. 각 막대를 100%로 맞춰야 그룹 사이 비교가 됩니다. 대신 **건수를 막대 오른쪽에 따로** 적습니다 — 3건짜리 100% 와 30건짜리 100% 를 같은 무게로 읽으면 안 되니까요

데이터가 없어 못 그린 장은 결과 dict 에 넣지 않고, 실행 끝에 어느 장이 빠졌는지 이름을 찍어줍니다.
분석이 0건인 경우처럼 **이유를 적을 수 있을 때는** 빈 축 대신 그 문장을 적은 그림을 남깁니다.
차트가 통째로 사라지면 리포트를 보는 사람이 빠뜨린 건지 없는 건지 구분할 수 없습니다.

### `bridge.py` — 외부 호출 창구 (261줄)

`main.py` 는 `source/` 나 `prompt/` 를 직접 import 하지 않습니다. 전부 이 파일을 거칩니다.
의존 방향은 **A → B, A → C 한 방향**이고, B/C 는 A를 import 하지 않습니다. 그래야 두 사람이 자기 폴더만으로 테스트할 수 있습니다.

초기에는 어댑터가 539줄이었는데 C와 합의해 계약을 맞추면서 절반 아래로 줄었습니다. 사라진 것들:

| 없앤 것 | 이유 |
|---|---|
| id 매핑 73줄 | C가 id 를 그대로 들고 다니게 됨 |
| 부분 실패 흡수 | C가 `failed_ids` 를 함께 반환 |
| stats 평면화 77줄 | 리포트 형식은 리포트를 만드는 쪽이 정함 |
| 배치 나누기 | C가 직접 배치로 부름 |
| mock 분기 | 연결 완료 |

**변환 코드가 줄어든 만큼 계약이 맞춰진 것**이라 보고 있습니다.

### `interfaces.py` — 계약 검증기 (410줄)

실행되는 문서입니다. `INTERFACE.md` 와 어긋나면 코드가 기준입니다.
`validate_stats` / `validate_analysis_output` / `validate_insights` / `validate_chart_paths` 네 개.
`validate_stats` 안에서 `alerts` 의 level·필수 키와 `keyword_impact` 의 정렬·범위까지 함께 봅니다.

`validate_chart_paths` 는 경로만 돌려주고 저장에 실패한 경우를 리포트 단계 **전에** 잡습니다. 파일 존재까지 확인합니다.
필수로 보는 것은 3장뿐입니다 — 나머지까지 필수로 걸면 데이터가 부족한 날 `dashboard` 가 통째로 멈춰서 통계도 리포트도 못 보게 됩니다.

### `exporter.py` — 내보내기 (231줄)

csv / jsonl / xlsx 세 형식. 두 가지를 신경 썼습니다.

- **CSV 에 BOM 을 붙입니다.** utf-8 로 쓰면 Excel 이 cp949 로 읽어 한글이 전부 깨집니다
- **openpyxl 이 없으면 xlsx 요청이 csv 로 떨어집니다.** 그때 요청 경로가 아니라 **실제 저장된 경로**를 반환합니다

     └─ A save_raw()                 → SQLite raw_reviews

### 자가 점검의 네 가지 표시

| 표시 | 뜻 |
|---|---|
| `[OK]` | 약속대로 동작 |
| `[FAIL]` | **만들었는데 약속과 다름.** 이것만 고치면 됨 |
| `[SKIP]` | 아직 안 만듦. 실패로 치지 않음 |
| `[TODO]` | 약속 위반이 아니라 **새로 부탁하는 것** |

`[TODO]` 를 `[FAIL]` 과 섞지 않은 이유가 있습니다.
전달 조건이 "자기 영역에 FAIL 없을 것" 이라, 새 요청이 빨간불로 뜨면 다 만든 사람도 빨간불이 되고
그러면 진짜 `[FAIL]` 을 보고도 아무도 안 움직이게 됩니다.

### 통합 테스트가 보는 것

계약이 깨지는 지점만 봅니다. B/C 의 기능 정확도는 각자 테스트가 있습니다.

- B의 clean 레코드 5개 필드가 DB 왕복에서 살아남는가 (`skin_type` 이 조용히 버려지지 않는가)
- 해시가 공백·대소문자를 정규화하는가 / 제품이 다르면 다른 리뷰로 잡는가
- C가 흔들려도 **id 가 사라지지 않는가** — `results` 아니면 `failed_ids` 중 한쪽에는 반드시 있어야 함
- 배치가 실패하면 반으로 쪼개 재시도해서 앞의 결과를 버리지 않는가
- `payload` 에 `rating` 이 섞이지 않는가
- `chart_data` 의 칸 이름과 `CHART_ORDER` 가 어긋나지 않는가
- KPI 가 `summary` 를 다시 세지 않고 옮겨오기만 하는가
- 그룹별 차트의 계열 길이가 labels 와 맞는가 (`zip` 이 조용히 자르지 않는가)
- 선택 필드가 전부 `None` 인 리뷰를 export 3형식이 처리하는가
- A가 B/C 폴더에 파일을 만들지 않았는가
- 걷어낸 모듈(`mock_ai.py` · `hashing.py`)이 되살아나지 않았는가
- 임계치를 넘으면 경고가 뜨고, **조용할 때는 조용한가** (항상 뜨는 경고는 경고가 아님)
- 표본이 작은 구간·그룹을 판정하지 않는가
- 별점이 흩어져 있는데 전부 긍정으로 찍히면 일치도 경고가 잡는가
- 불용어 어간이 모든 리뷰에 걸리지 않는가
- 본문에 없는 키워드가 `matched: false` 로 남는가
- Excel 의 빈 행이 걸러지고, 헤더만 있는 파일이 예외를 던지는가
- **경고가 콘솔뿐 아니라 로그에도 남는가**, 조용할 때는 로그도 조용한가
- 검수 표본이 **소수 감정을 전량 포함**하고, 같은 데이터면 같은 표본이 나오는가
- 검수자 두 사람이 갈리면 임의로 한쪽을 고르지 않고 따로 세는가
- 같은 회차·같은 사람이 다시 매기면 행이 늘지 않고 덮어써지는가
- 프롬프트 버전별 일치율이 나뉘어 나오는가 (A/B)
