# [프로젝트 1] 자동화 도구 비교 구현 보고서

## 합격 여부 통보 자동화 : Make vs Relay

---

## 1. 프로젝트 개요

동일한 자동화 워크플로우를 **Make**와 **Relay** 두 도구로 각각 구현하고, 구성 방식·실행 결과·사용성을 비교 분석한다.

| 항목 | 내용 |
| --- | --- |
| 자동화 목표 | 시험/평가 점수에 따라 합격·불합격 안내 메일 자동 발송 |
| 구현 도구 | ① Make (구 Integromat) ② Relay.app |
| 연동 서비스 | Google Forms, Google Sheets, Gmail |
| 분기 기준 | **점수 ≥ 85 → 합격 / 점수 < 85 → 불합격** |
| 산출물 | 도구별 워크플로우 캡처, 실행 결과 캡처, 비교 분석 보고서 |

---

## 2. 자동화 시나리오 (공통 설계)

응답자가 Google Form에 결과를 제출하면, 응답이 스프레드시트(응답지)에 자동 기록되고, 새 행이 감지되는 순간 점수 조건을 판별하여 합격/불합격 메일을 자동 발송한다.

```
Google Form (결과 통보지)
        │  응답 제출
        ▼
Responses Sheet (자동 생성 · 새 행 추가)
        │  새 행 감지 (Trigger)
        ▼
   조건 분기 (점수 판별)
      ┌──────────────┴──────────────┐
      ▼                             ▼
  점수 ≥ 85                      점수 < 85
   (합격)                         (불합격)
      │                             │
      ▼                             ▼
  Gmail 발송                    Gmail 발송
  (합격 안내)                    (불합격 안내)
```

핵심 3요소는 두 도구 모두 동일하다.

1. **Trigger** — 응답지(스프레드시트/폼)에 새 데이터가 들어오면 실행
2. **조건 분기** — 점수를 기준으로 두 갈래로 나눔
3. **Action** — 조건에 맞는 안내 메일을 Gmail로 발송

---

## 3. 도구별 구현

### 3-1. Make 구현

![Make 워크플로우 구성 화면](images/make_workflow.png)

**모듈 구성 (좌 → 우)**

| 순서 | 모듈 | 역할 |
| --- | --- | --- |
| ① | **Google Sheets — Watch New Rows** | 응답지에 새 행이 추가되면 트리거 실행 |
| ② | **Router** | 하나의 입력을 여러 경로(Route)로 분기 |
| ③ | **Gmail — Send an email** (Route 1) | `1st · 합격 통보` 경로 → 합격 안내 메일 발송 |
| ④ | **Gmail — Send an email** (Route 2) | `2nd · 불합격 통보` 경로 → 불합격 안내 메일 발송 |

**분기 방식 — Router + Filter**

Make는 **Router**로 흐름을 나눈 뒤, 각 경로의 연결선에 **Filter(필터)** 를 걸어 조건을 판별하는 구조다.

- Route 1 필터: `점수 ≥ 85` (합격) → 화면상 `✓ 1` = 1건 통과
- Route 2 필터: `점수 < 85` (불합격) → 화면상 `⊘ 0` = 0건 통과

즉 이번 실행에서는 합격 조건 1건이 통과되어 상단 Gmail(합격 메일)만 발송되었고, 불합격 경로는 통과 데이터가 없어 발송되지 않았다.

> **특징** : Router는 조건을 여러 개로 확장하기 쉽고(3분기, 4분기…), 각 경로마다 필터·번들 통과 수가 시각적으로 표시되어 어떤 데이터가 어디로 흘렀는지 즉시 파악할 수 있다.

### 3-2. Relay 구현

![Relay 워크플로우 구성 화면](images/relay_workflow.png)

**스텝 구성 (위 → 아래)**

| 순서 | 스텝 | 역할 |
| --- | --- | --- |
| 1 | **Instant trigger** — New response for `결과 통보지` is submitted | 폼 응답이 제출되는 즉시 실행 (상태 `On`) |
| 2 | **점수 숫자 변환** | 텍스트로 들어온 점수 값을 숫자 타입으로 변환 (조건 비교용 전처리) |
| 3 | **If** `점수 숫자 변환` is greater than or equal to 85 | 분기 조건 — 85점 이상 판별 |
| 4 | **Gmail — 합격 안내 이메일** | 합격 경로에서 안내 메일 발송 |

**분기 방식 — Condition (If / Path)**

Relay는 상단 탭 형태로 경로를 나눈다.

- **A · 합격 (85점 이상)** 탭 : `If 점수 ≥ 85` → 합격 안내 이메일
- **B · 불합격 (85점 미만)** 탭 : 별도 경로로 불합격 안내 이메일 구성

각 경로가 탭으로 분리되어 있어, 지금 어떤 조건 갈래를 편집 중인지 한눈에 들어온다. 위→아래로 읽는 선형 플로우라 초심자가 흐름을 따라가기 쉽다.

> **특징** : 조건 비교 전에 `점수 숫자 변환` 스텝을 명시적으로 두어야 한다는 점이 눈에 띈다. Relay는 데이터 타입에 다소 엄격해, 폼에서 문자열로 들어온 점수를 숫자로 변환하는 전처리가 필요하다.

## 4. 실행 결과

| 구분 | Make | Relay |
| --- | --- | --- |
| 트리거 발동 | 새 행 감지 정상 동작 | 폼 응답 제출 시 즉시 실행 (`On`) |
| 조건 판별 | 합격 경로 `1`건 통과 / 불합격 경로 `0`건 | `≥ 85` 조건 정상 통과 |
| 메일 발송 | 합격 안내 Gmail 발송 완료 | 합격 안내 이메일 발송 완료 |
| 결과 확인 방식 | 각 경로별 번들 통과 수(`✓1`, `⊘0`)로 시각 확인 | 스텝별 실행 로그 / Test 실행으로 확인 |

두 도구 모두 **동일한 입력(85점 이상 응답)에 대해 합격 안내 메일이 정상 발송**되어, 목표한 자동화 시나리오가 동등하게 구현됨을 확인했다.

**실제 발송 결과 (수신함 캡처본 확인)**


워크플로우 실행 후 수신함에 `[결과 통보]` 제목의 안내 메일이 실제로 도착한 것을 확인했다.

- `[결과 통보] 합격을 축하드립니다` — 합격 조건(≥ 85) 충족 시 발송된 합격 안내 메일
- `[결과 통보] 결과 안내` — 결과 통보 메일 발송

트리거 → 조건 분기 → Gmail 발송으로 이어지는 자동화 파이프라인이 **설계대로 끝단(메일 수신)까지 정상 동작**했음을 실물 결과로 입증했다.

## 5. 비교 분석

### 5-1. 구현 관점 비교

| 항목 | Make | Relay |
| --- | --- | --- |
| 분기 방식 | Router + Filter | Condition (If / Else, Path 탭) |
| UI | 캔버스 기반 시각적 노드 | 위→아래 선형 플로우 |
| 설정 | 세부 옵션이 많음 | 비교적 간단 |
| 데이터 전처리 | 인라인 함수로 유연하게 처리 | 별도 변환 스텝 필요 (예: 점수 숫자 변환) |
| 디버깅 | 단계별 데이터(번들) 확인이 매우 상세 | 실행 결과·로그 중심 |
| 확장성 | 다분기·복잡 로직에 강함 | 단순~중간 난이도 워크플로우에 적합 |
| 학습 난이도 | 조금 높음 | 낮음 |

### 5-2. 도구별 장단점

**Make**

- 장점 : 캔버스에서 데이터 흐름이 시각적으로 보이고, 각 모듈·필터의 통과 건수가 표시되어 디버깅이 직관적이다. Router로 다분기 확장이 쉽고 세부 설정이 풍부해 복잡한 로직도 구현 가능하다.
- 단점 : 옵션이 많은 만큼 초기 학습 곡선이 있고, 모듈·필터 개념을 익혀야 한다.

**Relay**

- 장점 : 위에서 아래로 읽는 선형 구조라 흐름 파악이 쉽고, 조건을 탭으로 나눠 관리가 명확하다. 진입 장벽이 낮아 빠르게 만들 수 있다.
- 단점 : 데이터 타입에 엄격해 전처리 스텝(숫자 변환 등)이 필요할 수 있고, 복잡한 다분기·정교한 데이터 가공에는 Make보다 유연성이 떨어진다.

---

## 6. 결론

동일한 "합격 여부 통보 자동화" 시나리오를 Make와 Relay 두 도구로 구현한 결과, **두 도구 모두 목표를 정상적으로 달성**했으며 최종 산출물(합격 안내 메일 발송)은 동일했다. 차이는 결과가 아니라 **구현 철학과 사용 경험**에서 나타났다.

- **복잡한 분기·정교한 데이터 가공·상세 디버깅**이 필요하다면 → **Make**
- **빠른 구축·직관적인 흐름·낮은 진입 장벽**이 우선이라면 → **Relay**

즉, 정형화된 단순 알림 자동화는 Relay로 빠르게, 조건이 늘어나고 데이터 가공이 복잡해지는 실무 자동화는 Make로 구축하는 것이 효율적이라는 결론을 얻었다.
